Bucket reading (lit-6000; chain/bare scale the same way, see section 6):
lex+parse ~0.2 s, linear (lexerr/parseerr rows). The parser is NOT the problem.
sourceerr ~0.3 s: the source phases THROUGH constant-scope discovery fail fast
on a bad scalar, so this row does NOT cover the later per-item meaning checks
or prepare; it only bounds lex..discovery on the failing path.
preparerr = 2*(source+prepare) + small, error-position independent (start=end):
whole-unit work before statement elaboration, quadratic (lit b 2.1, chain 1.9,
bare 1.4), shape-ordered lit >> chain > bare.
elaberr_e - elaberr_s = E_full-walk + ~11 extra bisection prefix elabs
(firstFailing, stage0/Stage0/Diagnose.lean:32-44, ~13 elabExpanded runs):
lit 1.89/8.17/40.51 (b ~2.3), chain 0.42/1.88/8.47 (b ~2.2),
bare 0.10/0.42/1.68 (b ~2.0). The elaborator path is superlinear for EVERY
shape, including binding-free bare calls.
full - preparerr/2 - E, with E ~= (elaberr_e - elaberr_s)/12 (bisection model,
~12 full-body equivalents): remainder R = lowering+checker+emission:
lit-1500/3000/6000 ~= 0.95/2.39/9.05 (b ~1.9, QUADRATIC);
bare-1500/3000/6000 ~= 0.37/0.44/0.76 (~linear).
So all three buckets (source+prepare, elaborator, lowering/checker) carry a
superlinear term for binding/guard-heavy bodies; bare-call bodies are ~linear
in R but still quadratic in the elaborator path (small constant).

5. One-sentence conclusions per series
--------------------------------------------------------------------------------
lit: cost per statement grows with the number of live bindings in scope
(flat memory, time ~N^2.0-2.2 through 12000), independent of calls.
chain: data-chained lets without guards are still ~N^1.9 (b 2.2 at 12k), so a
non-guard per-let/per-use scope-proportional step exists beside the guards.
call1: chained calls cost ~20% over chained plain ops at the same exponent, so
calls add a linear premium, not the quadratic term.
bare: N call statements with no new bindings are linear (b 0.99): the quadratic
needs bindings/uses, not calls or statements per se.
calln: N distinct callees cost the same as one callee with N independent
bound uses (18.4 vs 18.8 s): callee count is not the driver; the N bound uses
in one scope are.
guard: N guards on ONE binding are still superlinear (b 1.48): per-guard work
grows with body size even at constant scope (whole-block read walks, §7).
mut: N assignments to one binding are ~linear (b 0.86): assignment handling
accumulates nothing.
block: scoping the same statements in `if true` blocks of 100 makes it ~linear
(b 0.74): the driver is LIVE scope, not statement count; bounding it fixes it.
names/range/arity/spec: 40-char names = 5-char names; requires+ensures on the
callee = no contract (spec1 = call1); 0/2/6 params spread only ~15%; wide
range +12-15% at the same exponent (bigger words/images, not a new term).

  checker needs a mode the binary does not offer.
NOT the driver (measured): lexer/parser (0.1-0.2 s, linear); name length
(string compares); requires/ensures text; parameter count; duplicate-name scan
doppelterName (Stage0/Compiler.lean:21-26, Tafel-based); call count per se
(bare linear); statement count per se (block linear; mut linear).

10. Faults: none found on the way
--------------------------------------------------------------------------------
No compiler faults. All 16 shapes verify at N=10 (compile rc=0, run exit 7).
All five error triggers fail deterministically with the phase-correct message
(lex; item expected; scalar-range source error; generic-output residual for
prepare; name unknown + statement-locating note for elab). Side observation
(not a fault): statements after `return` are still elaborated (error fires),
and Diagnose.notes locates the failing statement (K of N) via prefix
bisection. SCALE findings F1 (f32/f64 callee names) and F2 (duplicate
cross-module names) were avoided by construction (distinct names) and not
re-tested.
