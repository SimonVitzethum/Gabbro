# `sperren.rangordnung` — das Korrektheitsargument

*Geschrieben am 2026-08-24. Der zweite Satz mit `ARGUED`.*

> **Das Ergebnis vorweg:** der Satz trägt, und er trägt aus einem Grund, den ich vor dem
> Nachsehen nicht kannte — **die gefährlichste Lücke ist konstruktiv geschlossen, nicht
> zufällig.** Ein indirekter Ruf kann die Rangordnung nicht unterlaufen, weil ein
> Funktionszeiger `locks` **gar nicht aussprechen darf**.

---

## 1. Was zu zeigen ist

**Der Satz:** ein Programm, das ohne Absage durchkommt, kann auf **deklarierten Sperren**
nicht verklemmen.

**Das Modell.** Endlich viele Sperren `L`, jede mit einem Rang `r(L) ∈ ℤ`. Ein Zustand ist eine
Menge von Fäden, jeder hält eine Menge von Sperren und wartet auf höchstens eine.

**Eine Verklemmung** ist ein **zirkuläres Warten**: Fäden `T₁ … Tₙ` und Sperren `L₁ … Lₙ` mit
*`Tᵢ` hält `Lᵢ₋₁` und wartet auf `Lᵢ`* (zyklisch).

---

## 2. Der Beweis, und er ist der klassische

**Was der Pass herstellt** (`geteilt.rs`, `rangordnung`): an jeder Nahmestelle von `L` unter der
gehaltenen Kette `C` gilt für alle `M ∈ C`

```rust
if *alt >= neu { … H006 … }        // abgesagt wird bei alt >= neu
```

also: **`r(M) < r(L)`, echt kleiner.**

**Argument.** Sei ein zirkuläres Warten gegeben. `Tᵢ` hält `Lᵢ₋₁` und fordert `Lᵢ` an; im
Augenblick der Anforderung war `Lᵢ₋₁` in der gehaltenen Kette, also `r(Lᵢ₋₁) < r(Lᵢ)`. Rundum:

```
r(L₁) < r(L₂) < … < r(Lₙ) < r(L₁)
```

ein Widerspruch in einer Totalordnung. Also gibt es kein zirkuläres Warten. ∎

**Gleichheit fällt mit**, und das ist der Grund für `>=` statt `>`: zwei Sperren gleichen Rangs
stehen in keiner Ordnung, zwei Halter können sie in zwei Richtungen nehmen — *genau daher
kommt eine Verklemmung.*

---

## 3. Die Prämissen, und jede ist eine Regel

| | die Prämisse | wer sie herstellt |
|---|---|---|
| **P1** | jeder Sperrname ist erklärt | **`H016`** |
| **P2** | jeder Rang steht zur Übersetzungszeit fest | **`H014`** |
| **P3** | die Kette wird über Aufrufgrenzen fortgesetzt | **`H012`** |

**P1 ist nicht kosmetisch, und das ist gemessen.** Vor `H016` schlugen `H006` und `H012` den
Rang eines unbekannten Namens nach, fanden nichts und **übersprangen still**:
`effects { locks NIEDA }` plus `locks NIEDA { … }` gab **null Fehler**. *Über eine
Bibliotheksgrenze war das nicht der Randfall, sondern der Normalfall.*

**P3 ebenso, seit 2026-08-19.** Davor ging `locks L2 { … nimmt_l1(); }` mit `L1` auf Rang 1
durch — *ein Zyklus über zwei Funktionen, und das ist genau die Gestalt, die eine echte
Kernverklemmung hat.* Nachgemessen am 2026-08-24:

```
Fehler: [H012] this call takes `A` (rank 1) while `B` (rank 2) is held here
   = the lock order runs UPWARDS, and it runs THROUGH calls
```

---

## 4. Der indirekte Ruf — die Lücke, die ich suchte, und sie ist zu

`K001` und `E008` rechnen mit dem Vertrag am **Zeigertyp**. Wenn ein Funktionszeiger `locks A`
zusagen könnte, ohne dass jemand die Kette dort fortsetzt, wäre die Ordnung durch jede
Dispatch-Tabelle zu unterlaufen. **Gemessen, beide Richtungen:**

```
type Ops = { tu : fn() effects { … locks A } … };
-> Fehler: [N036] `locks` cannot be promised at a function pointer type
   = the pass that reads this effect resolves the callee by NAME, and an indirect call
     has none -- `locks`, `masks`, `consumes` and `publishes` therefore do not cross one
   = this is a refusal and not an omission

return Ops(tu: &hart_tu);        -- hart_tu traegt `locks A`
-> Fehler: [M128] `fn()` does not fit `fn()`: it declares `locks A`,
                  which the slot does not allow
```

**Beide Türen sind zu.** Der Platz darf `locks` nicht sagen (`N036`), und eine Funktion, die
eine Sperre nimmt, passt in keinen Platz (`M128`).

> **Damit gilt der Satz auch in Gegenwart von Funktionszeigern — und der Preis steht daneben:
> eine Funktion, die eine deklarierte Sperre nimmt, ist heute NICHT über einen Zeiger
> erreichbar.** Dispatch-Tabelle und Sperrdisziplin schließen einander aus. *Das ist eine
> Aussage über die Reichweite der Sprache, keine über den Beweis — aber sie stand nirgends.*

---

## 5. Wo der Satz NICHT gilt

**(a) Über einer unvollständigen Hülle sagt der Pass nicht ab** (R16). Ein Pfad durch ein
`extern fn` ist nicht gedeckt — der Ruf verschwindet aus der Kette, statt sie zu verlängern.
*Das ist der dritte Zustand und richtig so; es heißt aber, dass der Satz an jeder fremden
Grenze endet.*

**(b) Nur deklarierte Sperren.** Ein Warten, das keine `lock` ist — ein Hardware-Handschlag,
die interne Sperre eines fremden Rumpfs, eine Warteschlange —, liegt außerhalb. **Die Klasse
„Verklemmung" ist damit größer als der Satz.**

**(c) Ränge sind ABSOLUTE Zahlen und komponieren nicht.** Die Vereinigung zweier unabhängig
geschriebener Bibliotheken ist nach der Zahlenwahl geordnet, die zufällig getroffen wurde —
`gabbro abi` trägt die `rank`-Zeile über die Grenze und `pruefe --with` rechnet die Ordnung
über der Vereinigung nach, aber **wenn zwei Bibliotheken denselben Rang für unverwandte
Sperren wählen, entsteht kein Fehler, sondern eine fehlende Ordnung.**

**(d) Der Satz sagt nichts über Fortschritt.** Keine Verklemmung heißt nicht: jeder Faden kommt
dran. *Aushungern ist eine andere Aussage, und dieser Pass macht sie nicht.*

---

## 6. Was `ARGUED` hier heißt

`sperren.rangordnung` steht auf **`ARGUED`**: §2 ist der Beweis, §3 nennt die drei Prämissen
samt der Regel, die jede herstellt, §4 schließt die Zeigerlücke mit einer Messung, §5 nennt
vier Ränder.

**Und was es nicht heißt.** Der Beweis in §2 setzt voraus, dass der Pass die Kette an **jeder**
Nahmestelle richtig führt — dass `rangordnung` über alle Anweisungsformen absteigt, in
Schleifenrümpfe, in `match`-Zweige, in `observes`-Blöcke. **Das habe ich nicht Fall für Fall
nachgesehen**, und es ist genau die Klasse, in der `enthaelt_schritt` und die Wirkungshülle
schon einmal zu flach lasen (W16).

> *Der Satz ist argumentiert. Der Abstieg unter ihm ist es nicht.* Er steht als offener Posten
> daneben und nicht als Fußnote.
