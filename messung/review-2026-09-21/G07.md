## Open findings, ranked

**F1 (severe — memory safety, costs, linearity; fixed in `49a8996d`, unbuilt).** Lane 227 lowers
an integer `match` to a `switch` with no `default` (`emit.rs` `match_int`). No Rust pass checks
that the arms cover the scrutinee: `intpat` is read only in `emit.rs`, and lane 228's
`erschoepfendB` is Lean only. Every flow pass still treated `match` as closed:

- `lib.rs::endet_immer` (master line 1443) and `m1.rs::endet_immer` (master 2333) answered
  "ends" whenever every arm returns;
- `m2.rs` (Match arm of `gehe`), `phasen.rs` (Match arm of `fluss`) and `arena.rs` joined only
  the arm states.

Concrete scenario, checker-clean on master by reading:

```gabbro
narrow i to 0 ..< 4 else { match y { 0 => { return 0; } } }
return T.slots[i].v;
```

`M105` stays silent, `M1` installs `i in 0 ..< 4`, and the C is
`if (!(i < 4)) { switch (y) { case 0: {...} break; } } return T->slots[i].v;`. With `i = 100` and
`y = 1` that is an out-of-bounds read.

The same misreading also:

- skips `S009` (`-> never` bodies), `S002` (`let … else`) and the `can_fail` rule;
- makes `kosten.rs` take a guarded early exit as always exiting, which under-counts costs;
- lets m2 book a linear value as consumed on every path (`match x { 0 => { nimm(m); } }`), which
  hides the leak.

Before lane 227 the emitter refused every integer match, so lane 227 is the one that made this
reachable. The branch fix is the conservative reading: an integer match is an `if` without
`else`. **The intended rule is still unbuilt:** a checker refusal of non-exhaustive integer
matches, under a new code from the untouched N411–415 block, with a sentence and a gift. That
belongs in TODO. `kosten.rs` `Match` (max over arms) was left as is, because the fall-through
path costs no more than the arms.

**F2 (medium — silent semantic change; fixed in `d905a859`, unbuilt).** `match_int` never compared
labels with the scrutinee's type. C converts a `case` constant to the promoted type of the
controlling expression, so over a `u32` scrutinee `-1 => …` is emitted as `case -1:` and fires for
`x == 4294967295`. The Gabbro arm names `-1`, and `CFormMatch` (`cases.lookup k` over `Int`)
never matches it. Whether gcc warns under `-Wall -Wextra` is **not measured**; `-Wsign-conversion`
is not in that set. Out-of-range positive labels over narrow types (`300` over `u8`) are probably
caught by gcc's `-Wswitch-outside-range`, which is on by default, but that was not measured either.

**F3 (medium — claim versus proof, lane 228).** Four problems:

- `CFormMatch.lean` calls `erschoepfendB` "what the checker runs" and says "a missing arm is a
  refusal downstream". Neither is built (see F1).
- The header and the report say the file "shows the denotation sound against the emitted
  `switch`". Nothing connects `fallListe`/`wahl` to the `cases` list of a concrete `CS.sw`.
  `exec_sw_hit` and `exec_sw_miss` just restate the constructors `Exec.swHit` and `Exec.swMiss`,
  and `SwDefExec` is a definition that no theorem ties to `Exec`.
- The witness `match_exhaustive_zeuge` evaluates the arms on two values read from the reference
  fixture, which is real. Its `refB_erreicht` and `refB_schreibt` conjuncts, however, are
  existing facts about a program that contains no `match`, so that part is decorative.
- The file has no SATZKARTE section, and the `pruefe-cformen.py` rows `stmt:switch-int` and
  `stmt:case-int` still name lane 228 as their owner, although 228 is merged without the lemma.

The CUTS comment is corrected in `cd9ced0d`. The report and the missing SATZKARTE entry are left
to the orchestrator.

**F4 (low-medium — fixed in `f3addbd2`, unbuilt).** `lean.rs` (`gabbro prove` exporter), in the
`StmtArt::Match` arm: an all-integer match has no variant names and no binders, so it fell into
the reason row and was exported as `.onReason g [("0", …), ("2 .. 4", …)]`. In `Body.lean`,
`.onReason` over a non-reason value is `.stuck`. The effect on proofs was not measured; it
probably fails closed. `lean_g.rs` already refused it (LG004).

**F5 (low — loud failure).** `int_fall_text` spells `-2^63` as `case -9223372036854775808:`. That
parses as `-(9223372036854775808)`, an unsigned constant, and gcc warns under `-Werror`. It is
loud, not silent, but it is a lowering `cc` refuses. The fix is `(-9223372036854775807 - 1)`
plus the `pruefe-cformen.py` regex.

**F6 (low).** Label expansion is capped at 256 per arm (`INTPAT_SPANNE`) but not per match. N wide
arms emit up to 256·N labels. Code size is linear in the source, not a safety issue.

**F7 (low — process).** `lane222_depth_stands_fourfold_over_corpus` fails whenever a corpus
example nests deeper than 8. Lane 227's report records that corpus files 147/148 were flattened
upstream to turn the test green again. A headroom test that edits examples measures the examples,
not the parser. The limit itself (`TIEFE_MAX`, `P038`) is the real guard.
