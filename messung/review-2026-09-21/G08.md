## Open findings, ranked

### F1 (HIGH, latent) — `N426` holds the ceiling against a LOWER bound: accepted programs reach the runtime `abort`

`crates/gabbro-check/src/arena.rs:199-214` (`vereinige`: committed joins with `min`),
`:512-537` (`verbinde_verpflichtung`: loops keep the min of entry and one-pass exit),
`:319-328` (`Stand::default()` per function: every body starts at the floor),
`:900-919` (`grow` checks `verpflichtung + n > M`). The min direction is right for "what is
usable" (future `R-commit`), wrong for "can this commit pass `M`", which needs the MAXIMUM over
paths and a widened value after loops. Concrete accepted shapes (`hi = 8`, `max 16`):

```
forever { grow A by 1 else { return 1; }; }                  -- loop: second walk sees 8 again
if c { grow A by 8 else { return 1; }; }  grow A by 8 else { return 2; };   -- join: min(16,8)=8
fn g() { grow A by 8 else {…}; }   fn h() { g(); g(); }        -- per function, per call
```

All three are accepted by `arena.rs` (read, not run). At run time the ninth iteration /
the second grow / the second call asks `committed + n > max`, and `gabbro_arena_grow` calls
`abort()` (`laufzeit/arena_dyn.c`). Today no emitted program reaches it because the emitter
refuses `grow` (`emit.rs`, `C001`); it becomes live the day lane 248's arm lands. The design
doc (`PLAN-DYNAMISCH.md` §4) prescribes this very direction, so the fix belongs in the design
first: carry `(count, committed_lo, committed_hi)`, `max`-join `committed_hi`, saturate it
past `M` after a loop whose body grows (unless the body resets first), and hold `N426`
against `committed_hi`; across functions, either book the ceiling as whole-program (like
counts) and say so in the sentence, or refuse `grow` outside a single designated owner. Must
be settled **before** the emitter arm lands.

Side detail in the same function (`arena.rs:917-920`): the `else` of `grow` runs from the
**bumped** state (`gabel` is called after the insert), contrary to PLAN §4 ("leaves
(count, committed) in the `else` branch"). Today that only over-refuses (a `grow` inside the
`else` can fall at `N426` spuriously); once `R-commit` is wired against the lower bound it
becomes unsound (a failed grow that falls through would count as committed). Fixing it alone
would currently widen F1 (the second example above would then pass), so fix both together.

### F2 (MEDIUM) — use-after-reset is refused per function only; calls and non-local indices escape `N211`

`arena.rs:708-712` (`StmtArt::Ruf` walks arguments, never moves a generation) and
`:1151-1154` (an index name that is neither `gebunden` nor `unsicher` — a parameter, a
global, a record field — is silent). Scenario:

```
arena A capacity 2 .. 2 of u16;
impl fn leere() effects { writes A } costs <= 4 ops { reset A; }
impl fn f() -> u32 effects { writes A } costs <= 32 ops {
    let a = alloc A (1);
    leere();
    let b = alloc A (2);          -- b == 0 == a at run time
    let x : u32 = A[a];           -- reads 2: stale index aliases the new slot, no N211
    return x;
}
```

Also `fn r(i : index into A) { reset A; … A[i] … }` and an index stored in a table field.
Memory safety holds (commit never shrinks, the index stays below `hi`/`committed`), so this is
a logical dangling reference, not an out-of-bounds access. But `ArenaReset.lean`'s CUTS
("there is no handle that outlives a `reset` to become dangling"), example 154's header ("no
live index past a reset") and PLAN §6 ("use-after-free falls out grammatically") state more
than the checker enforces. The module head of `arena.rs` books only the cross-function
**count**, not the cross-function **generation**. Either a call whose callee's effects write
`A` must consume `A`'s generation in the caller (cheap, sound), or the claim must shrink.

### F3 (MEDIUM) — the OOM `else` of `grow` is effectively unreachable on default Linux

`laufzeit/arena_dyn.c`, `gabbro_arena_grow`: `mprotect(PROT_READ|PROT_WRITE)` on a private
anonymous mapping succeeds under the default overcommit heuristic, and the following
`memset` then faults every new page in; out of memory shows up as the OOM killer (SIGKILL)
inside `memset`, not as `return false`. The (d) assumption text in MUSE-REPORT-242 §3
("either commits its slots … or takes the `else` branch") is therefore true only under
`vm.overcommit_memory=2` (or with a platform that fails `mprotect` on commit). The lane's
harness tested OOM only at reserve (`RLIMIT_AS`, exit 3), never the commit path. Also the
`memset` makes every commit eager (the zero-fill comment calls it defensive; freshly
`mprotect`ed anonymous pages are already zero). Name the overcommit condition in the
assumption text, or drop the `memset` for the fresh-mapping case and accept the kill as a
named hardware/runtime stop.
